──────────────────────────────────────────────────────────────────────────────
 4-1. 영상 무한 업로드 공격
──────────────────────────────────────────────────────────────────────────────
공격 방법:
  - 악성 계정 1개 생성 후 동일 방에 영상을 스크립트로 반복 업로드.
  - 현재 Free 플랜은 방당 10개 제한이 있으나, 이는 클라이언트 측에서만
    체크(checkProAccess)되기 때문에 API를 직접 호출하면 우회 가능.
  - Supabase Storage 비용은 저장 용량 + 전송량 기준으로 과금.

피해:
  - Storage 비용 폭증 (mp4 파일 다수 업로드 시 GB 단위 급증).
  - DB videos 테이블 row 폭증 → 쿼리 성능 저하.

대응 방안:
  1. RLS 정책에서 서버 측 업로드 건수 제한 추가.
     예) videos 테이블에 INSERT 정책:
       (SELECT COUNT(*) FROM videos WHERE room_id = NEW.room_id
        AND user_id = auth.uid()) < 10
     → Pro 여부는 profiles 테이블 tier 컬럼으로 서버에서 직접 판단.

  2. Supabase Storage Policy에서 파일 크기 상한 설정.
     Storage > Policies > max file size 설정 (예: 100MB 상한).

  3. 파일 확장자를 Storage 정책에서 video/* MIME만 허용.
     → 임의 파일 업로드 차단.

  4. 같은 유저가 단시간에 과도하게 업로드 시 차단하는
     DB Function 또는 Edge Function Rate Limit 적용.


──────────────────────────────────────────────────────────────────────────────
 4-2. 방(Room) 무한 생성 공격
──────────────────────────────────────────────────────────────────────────────
공격 방법:
  - 여러 계정을 생성하거나 단일 계정으로 방을 무한 생성.
  - 현재 Free 플랜 3개 제한은 클라이언트에서만 체크됨.
  - API 직접 호출로 우회 가능.

피해:
  - DB rooms 테이블 row 폭증.
  - 연관 데이터(members, videos, schedules 등)까지 연쇄 증가.

대응 방안:
  1. rooms 테이블 INSERT RLS 정책에서 방 개수 제한 서버 측 적용.
     예)
       CREATE POLICY "방 생성 제한"
       ON rooms FOR INSERT
       WITH CHECK (
         (SELECT COUNT(*) FROM room_members WHERE user_id = auth.uid()) < 3
         OR
         (SELECT subscription_tier FROM profiles WHERE id = auth.uid()) = 'pro'
       );

  2. Supabase Auth에서 계정 생성에 이메일 인증 필수화
     (현재도 적용 중인지 확인 필요).
     이메일 인증 없으면 일회용 메일로 계정 대량 생성 가능.

  3. 특정 이메일 도메인 차단 또는 일회용 이메일 차단 서비스 연동.


──────────────────────────────────────────────────────────────────────────────
 4-3. 공지사항·댓글·투표 무한 생성 공격
──────────────────────────────────────────────────────────────────────────────
공격 방법:
  - 동일 방에 공지사항·댓글·투표 옵션 등을 스크립트로 초당 수백 건 생성.
  - 현재 어떤 테이블에도 삽입 횟수 제한 정책 없음.
  - 멤버라면 누구나 가능.

피해:
  - DB row 수 폭증 → Supabase 무료 row 한도 초과 → 유료 전환 강제.
  - 실시간 구독(postgres_changes) 이벤트가 폭주 → 모든 클라이언트 성능 저하.
  - 방의 다른 멤버들에게 푸시 알림 스팸 발송.

대응 방안:
  1. 각 테이블 INSERT RLS 정책에 시간당 삽입 건수 제한 추가.
     예) notices 테이블:
       (SELECT COUNT(*) FROM notices
        WHERE user_id = auth.uid()
        AND created_at > NOW() - INTERVAL '1 hour') < 20

  2. video_comments, notice_comments, gallery_comments 등 댓글 테이블에도
     동일한 시간당 제한 적용.

  3. 투표 옵션(vote_options)은 투표당 최대 개수를 서버 정책에서 제한.

  4. 공지사항은 방장만 작성 가능하도록 RLS 정책 강화 검토.


──────────────────────────────────────────────────────────────────────────────
 4-4. 아카이브(사진·영상) 무한 업로드 공격
──────────────────────────────────────────────────────────────────────────────
공격 방법:
  - gallery_items 테이블에 직접 API 호출로 무한 삽입.
  - 동시에 Supabase Storage에 파일을 대량 업로드.
  - Free 플랜 20개 제한도 클라이언트에서만 체크됨.

피해:
  - Storage 비용 폭증.
  - gallery_items, gallery_comments row 폭증.

대응 방안:
  1. gallery_items INSERT RLS에 방당 항목 수 제한 추가 (영상과 동일).
  2. Storage Policy에서 gallery 버킷 파일 크기·MIME 타입 제한.
  3. 특히 영상 파일은 5MB 제한이 클라이언트에만 있으므로
     Storage Policy에서도 동일하게 max_file_size 설정 필수.


──────────────────────────────────────────────────────────────────────────────
 4-5. 푸시 알림 스팸 공격
──────────────────────────────────────────────────────────────────────────────
공격 방법:
  - 공지/영상/일정 등을 반복 생성하면 매번 방 멤버 전원에게 푸시 알림 발송.
  - 특히 大방(멤버 다수)에서 반복 생성 시 알림 수 폭증.
  - push-notification Edge Function을 직접 호출하면
    현재 별도 인증 없이 누구에게나 알림 발송 가능한지 확인 필요.

피해:
  - Push 알림 서비스(Expo Push / FCM / APNs) 발송 한도 초과.
  - 멤버들 기기에 알림 폭탄 → 앱 신뢰도 하락.

대응 방안:
  1. push-notification Edge Function에 호출자 인증(auth.uid 검증) 추가.
     인증된 멤버가 해당 방의 구성원인지 RLS 또는 함수 내부에서 검증.

  2. 알림 발송 횟수를 Edge Function 내에서 Redis/DB로 Rate Limit 적용.
     (예: 같은 유저가 1분 내 10회 이상 알림 트리거 시 차단)


──────────────────────────────────────────────────────────────────────────────
 4-6. 개발자 피드백 무한 전송 공격
──────────────────────────────────────────────────────────────────────────────
공격 방법:
  - developer_feedback 테이블에 스크립트로 대량 삽입.
  - 현재 어떤 제한도 없음.

피해:
  - DB row 폭증 (developer_feedback 테이블).
  - 실제 피드백이 스팸에 묻혀 확인 불가.

대응 방안:
  1. developer_feedback INSERT RLS에 시간당 삽입 제한 추가.
     예) 같은 user_id로 1시간 내 5건 이상 삽입 차단.
  2. 또는 로그인 상태에서만 삽입 가능하도록 RLS 정책 확인
     (현재 auth.uid() 체크가 있는지 확인 필요).


──────────────────────────────────────────────────────────────────────────────
 4-7. 계정 대량 생성 → 방 입장 시도 공격 (복합)
──────────────────────────────────────────────────────────────────────────────
공격 방법:
  - 일회용 메일로 계정을 대량 생성한 뒤 방 ID를 알아내고
    4자리 passcode를 브루트포스로 시도.
  - 방 입장 성공 후 내부 콘텐츠 열람 또는 스팸 업로드.

피해:
  - 사설 크루 정보 유출 (공지사항, 아카이브, 멤버 목록).
  - 방 내 스팸 콘텐츠 업로드.

대응 방안:
  1. passcode 입장 실패 횟수를 DB에 기록하고 n회 초과 시 일시 잠금.
  2. passcode 길이를 영숫자 6자리 이상으로 상향.
  3. 이메일 인증 없는 계정의 방 생성·입장 차단.
